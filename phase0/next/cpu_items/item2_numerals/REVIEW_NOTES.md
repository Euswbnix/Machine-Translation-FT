# item2_numerals: points still open after review (2026-10-19)

The headline numbers in README.md and every figure in results.json were re-derived by an independent check with its own code and agree. After one round of README edits, a second reviewer still found the wording and precision points below. Where they conflict with README.md, these notes are right; the README is to be corrected before any of it is quoted.

1. NEW WRONG CLAIM, README.md lines 242-247 ('Independent check' caveat). The sentence 'The differences move one rounding' (citing only ft_un_random -16.1 vs -16.0) is false. About 20 displayed values come out different at the README's own precision when compared with the checker. Three of them are listed in the checker's own problem text: ft_un_rep M2 mean 0.4559 vs 0.4558, ft_un_rep DATE share 1.17% vs 1.16%, and M2-key duplicate rate 12.30% vs 12.28%. The checker's summary adds ft_topk_rep M1 0.3681 vs 0.3682. scratchpad/item2_check/check_results.json adds more: ft_topk_rep M2 0.4393/0.4392, ft_un_div M2 0.0142/0.0141, ft_random_small M2 0.0811/0.0810 and fall -15.3%/-15.2%, table (c) DATE 0.73/0.72, 1.10/1.09, 1.01/1.00, 0.78/0.77, masked total 3.46/3.45, 3.12/3.11, 4.02/4.00, 3.24/3.23, SYM 0.777/0.775, 0.522/0.520, and the ft_un_random M2-key duplicate rate 1.06%/1.01%.

2. NEW UNDERSTATEMENT, same caveat. Three phrases understate the differences. (1) 'differ by a few rows or tokens': DATE token counts differ by hundreds (ft_un_rep 65,586 vs 65,262; ft_topk_rep 70,110 vs 69,651; ft_un_random 56,668 vs 55,818), and row counts by tens (whole-band M2 gain 29,309 vs 29,268; ft_un_div M2>0 16,024 vs 15,998). (2) 'Treat the last digit of regex-dependent counts as approximate': 29,309/29,268, 9,609/9,569 and 180/168 differ in the tens digit. (3) 'The largest relative differences are in small counts (113 against 116)': ft_random's M2<rep count, which README line 218 also prints, is 180 vs 168 (6.7%, against 2.6%). The ft_un_random M2-key duplicate rate differs by about 4% relative. The caveat should give the real size: at most about 0.02 pp on token shares, 0.0001 on means, and up to about 1.5% on date-token counts.

3. MINOR WORDING introduced by the scope fix, lines 202-204 and 211-213. Instead of 'upper bound on templated numerals', the text now calls the 4.8% and the 11.9% 'upper bounds on the repetition that runs through identical numerals'. But M1 measures exactly that quantity (up to the 33 strict-vs-loose rows), and it includes the verbatim whole-sentence reuse (kind 1). It is an upper bound only on the templated part, meaning kinds 2-3: fixed formulae and numbered openings with the same numbers. Suggest wording such as: '... an upper bound on templated numerals with fixed numbers; it cannot see templates whose numbers differ'.

4. MINOR, lines 228-231 plus Open point 1 (lines 258-260). The new sentence 'These are mixed-case codes, which match because the SYM regex requires only a capital first letter' makes the non-UN false positives sound like purely a mixed-case problem that an all-caps rule would fix. The not_A_E_S list in results.json also has all-caps non-UN matches that an all-caps rule would keep: NT/2000 ('Windows NT/2000', ft_topk.en line 568627), INS/ECAM3/2007 (a Cameroon national report, line 343973) and O/02 (from the OAS resolution 'XXXII-O/02', line 558780). The enumerated 'the non-UN ones are ...' list is therefore incomplete. It was probably there before the edit, but it now supports the open point's implication.
